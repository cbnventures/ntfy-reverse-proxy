Turn the alerts Discord Stonker Bot sends, such as a lost connection to Discord or a job that gave up, into ntfy notifications with the app's name before each title.

## Input Handling

The <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> reads the JSON alert that Discord Stonker Bot posts to a destination whose service is **ntfy-reverse-proxy**. Every field below is required, and fields that aren't listed are ignored.

| Field        | Type       | Description                                                               |
|--------------|------------|---------------------------------------------------------------------------|
| `version`    | `1`        | Payload format. Any other version fails.                                  |
| `app`        | `string`   | The app that sent the alert, which must be `discord-stonker-bot`.         |
| `event`      | `string`   | The event's key, such as `bot-disconnected`, or `test` for **Send test**. |
| `title`      | `string`   | The alert's title, such as `Bot disconnected`.                            |
| `message`    | `string`   | The alert's text.                                                         |
| `priority`   | `1-5`      | Priority level (1 = min, 3 = default, 5 = max).                           |
| `tags`       | `string[]` | ntfy tags, such as the emoji shortcode `warning`.                         |
| `occurredAt` | `string`   | When the alert happened.                                                  |
| `details`    | `object`   | Extra data about the alert.                                               |

The notification uses `title`, `message`, `priority`, and `tags`. The `event`, `occurredAt`, and `details` fields must be present, but they don't appear in it.

## Supported Events

Discord Stonker Bot sends these alerts, each with a fixed priority and tags:

| Title                      | Event Key            | Priority    | Tags               |
|----------------------------|----------------------|-------------|--------------------|
| Saved secrets were removed | `secrets-removed`    | 4 (high)    | `key`, `warning`   |
| Sign-in locked             | `sign-in-locked`     | 4 (high)    | `lock`             |
| Bot can't sign in          | `bot-sign-in-failed` | 4 (high)    | `x`                |
| Bot disconnected           | `bot-disconnected`   | 4 (high)    | `warning`          |
| Bot reconnected            | `bot-reconnected`    | 3 (default) | `white_check_mark` |
| Job gave up                | `job-failed`         | 4 (high)    | `x`                |
| Test notification          | `test`               | 3 (default) | `bell`             |

**Test notification** is what **Send test** sends, so a destination can't choose it as an event.

## Context Setup

1. **Add an HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>** — Run `nrp`, choose **Manage Contexts** > **Add**, pick **HTTP**, and choose **Discord Stonker Bot** as the **Interpreter**.
2. **Deploy** — Choose **Deploy**, then copy the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s URL and token from the **Context reference** list it prints.
3. **Add a destination** — On Discord Stonker Bot's **Notifications** page, select **Add notification**, choose **ntfy-reverse-proxy** as the **Service**, and paste the URL into **Context URL**. Paste the token into **Context token** if the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> has one, enter a **Name**, and select **Add notification** to save it.
4. **Send a test** — Select **Send test** on the destination, and check that `[Discord Stonker Bot] Test notification` arrives on the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s <Terminology title="The ntfy channel your phone subscribes to for alerts" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>.

Under **Context URL**, the dialog reminds you with `Set the context's interpreter to discord-stonker-bot.`

```json
{
  "id": "discord-stonker-bot-example",
  "name": "Discord Stonker Bot",
  "type": "http",
  "interpreter": "discord-stonker-bot",
  "topic": "discord-bot",
  "mode": "send-once",
  "show_visitor_info": false,
  "primary_server": "primary",
  "servers": ["primary"],
  "token": "replace_with_auth_token"
}
```

With this <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>, Discord Stonker Bot posts its alerts to `https://discord-stonker-bot-example.ntfy.example.com`.

## Notification Output

- **Title**: `[Discord Stonker Bot]` and the alert's `title` (e.g., `[Discord Stonker Bot] Bot disconnected`).
- **Body**: The alert's `message`, with HTML tags removed as for every <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> (see [HTML Stripping](/docs/interpreters/limitations/#html-stripping)).
- **Priority**: The alert's `priority`, unchanged. Discord Stonker Bot sends `4` for high-priority events and `3` for the rest.
- **Tags**: `discord-stonker-bot` first, then the alert's `tags` (e.g., `discord-stonker-bot`, `warning`).

The <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> sets no icon, actions, or Markdown.

## Example

Discord Stonker Bot posts this alert when it has been off Discord for a minute:

```json
{
  "app": "discord-stonker-bot",
  "details": {
    "downSince": "2026-10-26T12:00:00.000Z"
  },
  "event": "bot-disconnected",
  "message": "The bot lost its connection to Discord and hasn't reconnected after a minute. Features that need Discord are paused until it does.",
  "occurredAt": "2026-10-26T12:01:00.000Z",
  "priority": 4,
  "tags": ["warning"],
  "title": "Bot disconnected",
  "version": 1
}
```

The proxy publishes it to ntfy with these <Terminology title="The X-Title, X-Priority, and friends sent to ntfy" to="/docs/reference/terminology#ntfy-servers-and-messages">ntfy headers</Terminology> and body:

```text
X-Title: [Discord Stonker Bot] Bot disconnected
X-Priority: 4
X-Tags: discord-stonker-bot,warning

The bot lost its connection to Discord and hasn't reconnected after a minute. Features that need Discord are paused until it does.
```

ntfy shows the `warning` tag as an emoji and lists `discord-stonker-bot` below the notification.

## Wrong App Error

A <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> reads alerts from one app, so a payload whose `app` names a different app fails instead of arriving under the wrong name. When that app has a built-in <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>, the proxy answers with HTTP 422 and names the interpreter to use:

```json
{
  "status": "error",
  "message": "This context reads Discord Stonker Bot alerts, but the payload came from outpost. Set the context's interpreter to outpost."
}
```

If `app` contains an unknown producer key, the error instead says the app is unsupported and lists the supported interpreter keys. It never recommends configuring the unknown value.

- **Fix** — Set the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s `interpreter` to the key the message names, or point that app at a <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> that uses its own <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>.
- **Send test** — The sending app reports that the test couldn't be sent, with `HTTP 422` and up to 120 characters of this message as the reason.
- **Error topic** — If the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> has an `error_topic` and `error_events` includes `interpretation` (or is omitted), the proxy also sends an `Interpretation Error` with `error-debug.json` to that <Terminology title="Where you hear about alerts the proxy couldn't handle" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>.
- **Other payloads** — A non-empty body that isn't JSON, or JSON that isn't an alert (such as one without `title`, or with a `version` other than `1`), also fails with HTTP 422 before the app is checked.
