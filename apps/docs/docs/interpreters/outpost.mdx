Turn the alerts Outpost sends, such as updated containers or a failed update, into ntfy notifications with the app's name before each title.

## Input Handling

The <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> reads the JSON alert that Outpost posts to a destination whose service is **ntfy-reverse-proxy**. Every field below is required, and fields that aren't listed are ignored.

| Field        | Type       | Description                                                            |
|--------------|------------|------------------------------------------------------------------------|
| `version`    | `1`        | Payload format. Any other version fails.                               |
| `app`        | `string`   | The app that sent the alert, which must be `outpost`.                  |
| `event`      | `string`   | The event's key, such as `update-failed`, or `test` for **Send test**. |
| `title`      | `string`   | The alert's title, such as `Update failed`.                            |
| `message`    | `string`   | The alert's text.                                                      |
| `priority`   | `1-5`      | Priority level (1 = min, 3 = default, 5 = max).                        |
| `tags`       | `string[]` | ntfy tags, such as the emoji shortcode `whale`.                        |
| `occurredAt` | `string`   | When the alert happened.                                               |
| `details`    | `object`   | Extra data about the alert.                                            |

The notification uses `title`, `message`, `priority`, and `tags`. The `event`, `occurredAt`, and `details` fields must be present, but they don't appear in it.

## Supported Events

Outpost sends these alerts, each with a fixed priority and tags:

| Title                      | Event Key           | Priority    | Tags                        |
|----------------------------|---------------------|-------------|-----------------------------|
| Saved secrets were removed | `secrets-removed`   | 4 (high)    | `key`, `warning`            |
| Sign-in locked             | `sign-in-locked`    | 4 (high)    | `lock`                      |
| Containers updated         | `updates-applied`   | 3 (default) | `whale`, `white_check_mark` |
| New images available       | `updates-available` | 3 (default) | `whale`                     |
| Update failed              | `update-failed`     | 4 (high)    | `whale`, `warning`          |
| Test notification          | `test`              | 3 (default) | `bell`                      |

- **Update failed** — Outpost also sends it when a whole update check couldn't run.
- **Test notification** — It's what **Send test** sends, so a destination can't choose it as an event.

## Context Setup

1. **Add an HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>** — Run `nrp`, choose **Manage Contexts** > **Add**, pick **HTTP**, and choose **Outpost** as the **Interpreter**.
2. **Deploy** — Choose **Deploy**, then copy the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s URL and token from the **Context reference** list it prints.
3. **Add a destination** — On Outpost's **Notifications** page, select **Add notification**, choose **ntfy-reverse-proxy** as the **Service**, and paste the URL into **Context URL**. Paste the token into **Context token** if the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> has one, enter a **Name**, and select **Add notification** to save it.
4. **Send a test** — Select **Send test** on the destination, and check that `[Outpost] Test notification` arrives on the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s <Terminology title="The ntfy channel your phone subscribes to for alerts" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>.

Under **Context URL**, the dialog reminds you with `Set the context's interpreter to outpost.`

```json
{
  "id": "outpost-example",
  "name": "Outpost",
  "type": "http",
  "interpreter": "outpost",
  "topic": "containers",
  "mode": "send-once",
  "show_visitor_info": false,
  "primary_server": "primary",
  "servers": ["primary"],
  "token": "replace_with_auth_token"
}
```

With this <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>, Outpost posts its alerts to `https://outpost-example.ntfy.example.com`.

## Notification Output

- **Title**: `[Outpost]` and the alert's `title` (e.g., `[Outpost] Update failed`).
- **Body**: The alert's `message`, with HTML tags removed as for every <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> (see [HTML Stripping](/docs/interpreters/limitations/#html-stripping)).
- **Priority**: The alert's `priority`, unchanged. Outpost sends `4` for high-priority events and `3` for the rest.
- **Tags**: `outpost` first, then the alert's `tags` (e.g., `outpost`, `whale`, `warning`).

The <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> sets no icon, actions, or Markdown.

## Example

Outpost posts this alert when it rolls back a container that failed its update:

```json
{
  "app": "outpost",
  "details": {
    "containers": [
      {
        "container": "api",
        "image": "ghcr.io/example/api:2",
        "status": "rolled-back",
        "detail": "New container is unhealthy; rolled back to the previous container"
      }
    ],
    "finishedAt": "2026-10-26T04:01:12.480Z"
  },
  "event": "update-failed",
  "message": "Couldn't update 1 container: api (ghcr.io/example/api:2) was rolled back: New container is unhealthy; rolled back to the previous container.",
  "occurredAt": "2026-10-26T04:01:12.503Z",
  "priority": 4,
  "tags": ["whale", "warning"],
  "title": "Update failed",
  "version": 1
}
```

The proxy publishes it to ntfy with these <Terminology title="The X-Title, X-Priority, and friends sent to ntfy" to="/docs/reference/terminology#ntfy-servers-and-messages">ntfy headers</Terminology> and body:

```text
X-Title: [Outpost] Update failed
X-Priority: 4
X-Tags: outpost,whale,warning

Couldn't update 1 container: api (ghcr.io/example/api:2) was rolled back: New container is unhealthy; rolled back to the previous container.
```

ntfy shows the `whale` and `warning` tags as emoji and lists `outpost` below the notification.

## Wrong App Error

A <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> reads alerts from one app, so a payload whose `app` names a different app fails instead of arriving under the wrong name. When that app has a built-in <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>, the proxy answers with HTTP 422 and names the interpreter to use:

```json
{
  "status": "error",
  "message": "This context reads Outpost alerts, but the payload came from transmission-vpn. Set the context's interpreter to transmission-vpn."
}
```

If `app` contains an unknown producer key, the error instead says the app is unsupported and lists the supported interpreter keys. It never recommends configuring the unknown value.

- **Fix** — Set the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s `interpreter` to the key the message names, or point that app at a <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> that uses its own <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>.
- **Send test** — The sending app reports that the test couldn't be sent, with `HTTP 422` and up to 120 characters of this message as the reason.
- **Error topic** — If the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> has an `error_topic` and `error_events` includes `interpretation` (or is omitted), the proxy also sends an `Interpretation Error` with `error-debug.json` to that <Terminology title="Where you hear about alerts the proxy couldn't handle" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>.
- **Other payloads** — A non-empty body that isn't JSON, or JSON that isn't an alert (such as one without `title`, or with a `version` other than `1`), also fails with HTTP 422 before the app is checked.
