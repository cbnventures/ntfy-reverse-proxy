Use the CLI to manage `config.json`, validate settings, generate `wrangler.toml`, and deploy to Cloudflare Workers.

## Overview

The CLI manages the `config.json` file that the Cloudflare <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">Worker</Terminology> reads at runtime. You can run it in two ways:

- **Interactive mode** — `nrp` (no arguments) launches a TUI menu.
- **Direct commands** — `nrp <command>` for scripting and automation.

`ntfy-reverse-proxy` and `nrp` are registered as CLI aliases. To run it once without installing, use `npx ntfy-reverse-proxy`.

When working inside a clone of the repository, the same CLI is available as `npm run manage` and `npm run manage <command>`.

## Interactive Menu

When launched without arguments, the CLI presents a menu with these options:

- **Manage Servers** — Manage ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> definitions (submenu: add, edit, remove).
- **Manage Contexts** — Manage notification <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> (submenu: add, edit, remove).
- **Settings** — View and update global settings (<Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> name, <Terminology title="The domain every context subdomain lives under" to="/docs/reference/terminology#cloudflare-setup">base domain</Terminology>, <Terminology title="Shows what happened inside the proxy, secrets masked" to="/docs/reference/terminology#configuration">debug output</Terminology>).
- **Deploy** — Validate config, verify Cloudflare permissions, create <Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology>, generate `wrangler.toml`, deploy the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology>, and configure email routing — all in one step.
- **Exit** — Exit the CLI.

The interactive menu uses `prompts` for terminal UI. It walks you through each field with validation.

### Server Submenu

- **Add** — Prompts for name, <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> URL (must start with `https://`), and token (must start with `tk_`).
- **Edit** — Select an existing <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology>, then update its URL, which starts filled in with the current one, or its token. Leave the token blank to keep the current one.
- **Remove** — Select a <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> to remove. Fails if any <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> references it.

### Context Submenu

- **Add** — Prompts for the type (HTTP or email), name, ID, <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>, <Terminology title="The ntfy channel your phone subscribes to for alerts" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>, <Terminology title="Where you hear about alerts the proxy couldn't handle" to="/docs/reference/terminology#ntfy-servers-and-messages">error topic</Terminology> and the errors that notify it, delivery mode, visitor info toggle, <Terminology title="The ntfy server send-once tries first" to="/docs/reference/terminology#ntfy-servers-and-messages">primary server</Terminology>, and the <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">servers</Terminology> to use. It ends with <Terminology title="A short-lived, one-use pass a sender gets from /session" to="/docs/reference/terminology#configuration">session tokens</Terminology> or an auth token for an HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> or an allowed sender for an email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>, and it requires at least one <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> to exist first.
- **IDs and tokens** — Leaving the ID blank gives an HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> a generated 20-character lowercase ID. A manually entered HTTP ID must be a 1–63 character DNS host label made of lowercase letters, digits, and interior hyphens. An email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> needs an ID you choose, since it becomes the address's local part. The suggested auth token is a generated 64-character mixed-case string, and clearing it leaves the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> without a token.
- **Session tokens** — Answering yes to **Use session tokens?** generates the 64-character session secret and skips the auth token prompt. The two can't be combined.
- **Interpreter choices** — HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> offer Plain Text, ntfy JSON, Seerr, Synology DSM, Statuspage.io, Transmission VPN, pfSense Actions, Discord Stonker Bot, Outpost, and Mailmask. Email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> offer Plain Text, pfSense, and UniFi.
- **Edit** — Select an existing <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>, then step through the same fields with the current values filled in. You can keep the ID; choosing a new HTTP ID generates one, while choosing a new email ID prompts for its replacement local part. You can also turn <Terminology title="A short-lived, one-use pass a sender gets from /session" to="/docs/reference/terminology#configuration">session tokens</Terminology> on or off, which removes the auth token when they turn on, keep or regenerate an HTTP auth token, add a token to an HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> without one, or clear an email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s allowed sender.
- **Remove** — Select a <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> to remove.

:::info
<Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">Context</Terminology> tokens do not use the `tk_` prefix — that format is only for <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> tokens. <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">Context</Terminology> tokens are 64-character mixed-case alphanumeric strings auto-generated by the CLI.
:::

## Commands

:::info
Changes to `config.json` reach the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">Worker</Terminology> only after the next deploy. That's why `server remove`, `context remove`, and the menu's **Remove** and **Settings** remind you to run `nrp deploy`.
:::

### `server remove <name>`

Removes a <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> definition by name. Fails if the named server does not exist, or if any <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> still references it in `primary_server` or `servers` — you will need to update those <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> first.

### `context remove <name>`

Removes a <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> by name. Fails if the named context does not exist.

### `validate`

Validates the current config file. Checks:

- Schema validation (required fields, correct types, and no unknown <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> keys)
- <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">Server</Terminology> reference integrity (all `primary_server` and `servers` entries point to existing <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">servers</Terminology>, and each `primary_server` is in its <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s `servers`)
- No duplicate <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> IDs

Prints each error it finds, and exits with code 1 when the config is invalid.

### `generate`

Generates a `wrangler.toml` file from the config and writes it next to your `config.json`, plus a <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">Worker</Terminology> entry and a copy of the config in `.wrangler/ntfy-reverse-proxy/` beside it. The generated `wrangler.toml` includes:

- <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">Worker</Terminology> name, compatibility date, and main entry pointing to the generated entry, which imports the Worker included with the installed package
- Routes array with `{context-id}.{base_domain}` patterns for each HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>
- Email routing section showing required forwarding addresses for email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology>
- No <Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology> binding, which only `deploy` adds after it creates or finds the namespace

### `deploy`

Runs the full deployment pipeline:

1. Resolves the Cloudflare API token from `CLOUDFLARE_API_TOKEN` in the environment or a `.env` file. When none works, **Deploy** in the interactive menu prompts for one and saves it to the `.env` file in your config directory, while `nrp deploy` stops with an error.
2. Validates config integrity.
3. Verifies Cloudflare API permissions (Workers, KV, and optionally Email Routing).
4. Creates or locates a <Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology> for Statuspage deduplication and session tokens.
5. Generates `wrangler.toml`.
6. Deploys the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> via Wrangler.
7. Configures <Terminology title="Lets an email address trigger the proxy like a webhook" to="/docs/reference/terminology#cloudflare-setup">Cloudflare Email Routing</Terminology> rules for email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> (if any).
8. Prints a summary of deployed URLs and email addresses.

## Config File Resolution

The CLI looks for config files in this order:

1. Current working directory.
2. Project root directory.
3. Platform-specific config directory.

If no `config.json` is found, the CLI copies the starter template bundled with the npm package to the default config directory. When `nrp` opens the interactive menu and finds `config.json` in more than one of these places, it asks which one to use, while commands use the first one found.

:::tip
The CLI also checks for `.env` files in the same locations and loads environment variables from the first one found. The `CLOUDFLARE_API_TOKEN` variable is used for deployment.
:::
