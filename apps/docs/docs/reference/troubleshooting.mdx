Diagnose and fix common issues when deploying and operating Reverse Proxy for ntfy.

## DNS_PROBE_FINISHED_NXDOMAIN

**Symptom**: Browser or curl reports that the domain cannot be resolved.

**Cause**: The <Terminology title="Workers route treating the hostname's first label as subdomain" to="/docs/reference/terminology#custom-domain-route">custom domain route</Terminology> was deployed but Cloudflare has not created the DNS record yet, or DNS has not propagated.

**Solution**:

- Wait a few minutes after deployment — Cloudflare auto-creates DNS records for <Terminology title="Workers route treating the hostname's first label as subdomain" to="/docs/reference/terminology#custom-domain-route">custom domain routes</Terminology>.
- Check **Dashboard > DNS > Records** for a record matching your subdomain.
- Check **Dashboard > Workers & Pages > ntfy-reverse-proxy > Settings > Domains & Routes** for the custom domain entry.
- Verify propagation with `dig {context-id}.ntfy.example.com`.

## ERR_SSL_VERSION_OR_CIPHER_MISMATCH

**Symptom**: Browser shows an SSL error when accessing a custom domain.

**Cause**: Cloudflare has not provisioned the SSL certificate for the new custom domain yet.

**Solution**:

- Wait up to 15 minutes for certificate provisioning.
- Check **Dashboard > SSL/TLS > Edge Certificates** for the certificate status.
- Verify your SSL/TLS mode is "Full" or "Full (strict)" in **Dashboard > SSL/TLS > Overview**.

## 403 Forbidden (Cloudflare HTML Page)

**Symptom**: POST requests return a Cloudflare "Sorry, you have been blocked" HTML page instead of the <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology>'s JSON response.

**Cause**: <Terminology title="Cloudflare feature that can block automated webhook requests" to="/docs/reference/terminology#bot-fight-mode">Bot Fight Mode</Terminology> or WAF rules are blocking automated HTTP requests (webhooks, curl, etc.).

**Solution**:

- Disable <Terminology title="Cloudflare feature that can block automated webhook requests" to="/docs/reference/terminology#bot-fight-mode">Bot Fight Mode</Terminology>: **Dashboard > Security > Bots > Bot Fight Mode > Off**.
- Or create a WAF skip rule: **Dashboard > Security > WAF > Custom Rules**:
  - If: `(http.host contains "ntfy.example.com")`
  - Then: Skip > All Super Bot Fight Mode Rules
  - Place at: First

:::warning
<Terminology title="Cloudflare feature that can block automated webhook requests" to="/docs/reference/terminology#bot-fight-mode">Bot Fight Mode</Terminology> cannot be skipped via WAF rules on any plan. The skip rule above targets <Terminology title="Pro-plan Bot Fight Mode variant that can be skipped" to="/docs/reference/terminology#bot-fight-mode">Super Bot Fight Mode</Terminology>, which is available on Pro plans and above. Free plan users will need to disable <Terminology title="Cloudflare feature that can block automated webhook requests" to="/docs/reference/terminology#bot-fight-mode">Bot Fight Mode</Terminology> entirely if it blocks webhook traffic. You can also use a `sec-fetch-mode` header check to distinguish browser traffic from API traffic (see [Security](/docs/features/security/)).
:::

## TLS Handshake Failure from Docker Containers

**Symptom**: Docker containers (e.g., Watchtower) fail with `remote error: tls: handshake failure` when sending to the proxy.

**Cause**: The container's CA certificate bundle is outdated. Cloudflare's edge certificates may chain through a CA that the container does not trust.

**Solution**: Mount the host's CA certificates into the container:

```bash
docker run -v /etc/ssl/certs:/etc/ssl/certs:ro ...
```

On Synology NAS, the cert path is `/etc/ssl/certs/`. Add this volume mount and restart the container.

## 404 Not Found

**Symptom**: POST requests return a JSON error like `{"status": "error", "message": "No context found for http identifier: ..."}`.

**Cause**: The request subdomain does not match any configured <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> ID.

**Solution**:

- Check that the <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> ID matches the subdomain: a request to `abc123.ntfy.example.com` needs a <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> with `"id": "abc123"`.
- Run `nrp validate` to check for config issues.
- Re-deploy after config changes — the <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology> reads config from environment variables injected at deploy time.

## 403 Authentication Failed

**Symptom**: POST requests return HTTP 403 from the <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology> with `{"status": "error", "message": "Unauthorized"}`.

**Cause**: The <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> has a `token` configured and the request does not include a matching `Authorization` header.

**Solution**:

- Include the header: `Authorization: Bearer {context-token}`.
- Both `Bearer {token}` and raw `{token}` formats are accepted.
- Check that the token matches exactly — it is case-sensitive.

## 422 Interpretation Failed

**Symptom**: POST requests return HTTP 422 with an error message from the <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology>.

**Cause**: The <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology> could not parse the request body. The payload does not match the expected shape for the configured <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology>.

**Solution**:

- Check that the correct <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology> is configured for your webhook source.
- For `ntfy-json`, verify the payload includes the required `body` field.
- For service-specific <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreters</Terminology>, check that the payload matches the expected format (see individual [interpreter docs](/docs/interpreters/overview/)).
- Enable `show_response_output` temporarily to see detailed error information in the response.

## Notifications Not Arriving

**Symptom**: The proxy returns 200 but notifications do not appear in ntfy.

**Solution**:

- Check that the ntfy <Terminology title="an ntfy instance defined by name, URL, and token" to="/docs/reference/terminology#server">server</Terminology> is reachable and the token is valid.
- Verify the ntfy <Terminology title="an ntfy instance defined by name, URL, and token" to="/docs/reference/terminology#server">server</Terminology> has `behind-proxy` set to `true` and `base-url` configured.
- Enable `show_response_output` to see per-<Terminology title="an ntfy instance defined by name, URL, and token" to="/docs/reference/terminology#server">server</Terminology> delivery results in the response JSON.
- Check ntfy <Terminology title="an ntfy instance defined by name, URL, and token" to="/docs/reference/terminology#server">server</Terminology> logs for authentication or <Terminology title="the ntfy channel a context publishes notifications to" to="/docs/reference/terminology#topic">topic</Terminology> permission errors.
- For binary <Terminology title="a binary file delivered alongside a notification" to="/docs/reference/terminology#attachment">attachments</Terminology> (images, files), verify `attachment-cache-dir` is configured on the ntfy <Terminology title="an ntfy instance defined by name, URL, and token" to="/docs/reference/terminology#server">server</Terminology>. Large text messages are handled by the proxy's <Terminology title="splits message bodies over 4000 UTF-8 bytes into parts" to="/docs/reference/terminology#smart-split">message splitting</Terminology> and do not require this setting.

## Email Notifications Not Working

**Symptom**: Emails sent to `{context-id}@{base_domain}` do not produce notifications.

**Solution**:

- Verify <Terminology title="Cloudflare feature that forwards email to the Worker" to="/docs/reference/terminology#cloudflare-email-routing">Cloudflare Email Routing</Terminology> is enabled for your domain.
- Check that a routing rule exists for the email address pointing to your <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology>.
- Verify the <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> type is `"email"` (not `"http"`).
- Check the `allowed_from` field — if set, the sender must match.
- Email processing is silent — there are no HTTP error responses for failed email processing.

:::tip
If the <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> has an `error_topic` configured, authentication and interpretation errors from email processing are forwarded there as debug <Terminology title="a binary file delivered alongside a notification" to="/docs/reference/terminology#attachment">attachments</Terminology>. If the <Terminology title="a notification source configuration" to="/docs/reference/terminology#context">context</Terminology> also has an `error_events` setting, only the listed categories are forwarded. Check that <Terminology title="optional topic that receives failure notifications" to="/docs/reference/terminology#error-topic">topic</Terminology> for diagnostic information.
:::

## Duplicate Statuspage Notifications

**Symptom**: You receive the same Statuspage.io notification multiple times.

**Cause**: Without KV storage, the Statuspage <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology> cannot deduplicate updates. The <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology> uses the `updateId` field from incident updates to detect duplicates.

**Solution**:

- Run `deploy` from the interactive menu — it automatically creates a <Terminology title="Cloudflare Workers KV store for dedup state" to="/docs/reference/terminology#kv-namespace">KV namespace</Terminology> named `{worker_name}-kv` and binds it to the <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology>.
- If deploying manually, create a Cloudflare Workers <Terminology title="Cloudflare Workers KV store for dedup state" to="/docs/reference/terminology#kv-namespace">KV namespace</Terminology> and provide its ID during `wrangler.toml` generation.
- The <Terminology title="module that transforms a payload into a notification" to="/docs/reference/terminology#interpreter">interpreter</Terminology> stores incident state with a 24-hour TTL and skips duplicate update IDs.

## 405 Method Not Allowed

**Symptom**: Requests return HTTP 405 with a "Method not allowed" error.

**Cause**: The <Terminology title="Cloudflare-hosted entry point that runs the pipeline" to="/docs/reference/terminology#worker">worker</Terminology> only accepts `GET`, `POST`, and `PUT` requests. Other HTTP methods (e.g., `DELETE`, `PATCH`) are rejected.

**Solution**:

- Verify the webhook source is sending `POST` or `PUT` requests.
- `GET` requests return the <Terminology title="HTML status page returned on GET requests" to="/docs/reference/terminology#landing-page">landing page</Terminology>, so use `POST` or `PUT` for webhook delivery.
