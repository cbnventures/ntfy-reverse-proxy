Set up Reverse Proxy for ntfy from scratch and send your first push notification through Cloudflare Workers.

## Prerequisites

Before you begin, make sure you have the following ready:

- **Node.js** — v22, v24, or v26 (LTS recommended for stability)
- **npm** — v10 or later, which ships with supported Node.js versions
- **Cloudflare account** — A free or paid account with a registered domain (Workers and Email Routing are both available on the free plan)
- **ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology>** — At least one self-hosted ntfy instance with token authentication enabled

:::info
Your ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> needs `base-url` set to its public URL and `behind-proxy` set to `true`. If you plan to use an <Terminology title="Where you hear about alerts the proxy couldn't handle" to="/docs/reference/terminology#ntfy-servers-and-messages">error topic</Terminology>, also configure `attachment-cache-dir`, because error details arrive as an `error-debug.json` <Terminology title="A file sent along with the notification" to="/docs/reference/terminology#ntfy-servers-and-messages">attachment</Terminology>.

See the [ntfy self-hosting documentation](https://docs.ntfy.sh/config/) for details.
:::

## Install

Install the package globally to use the `nrp` command anywhere:

```bash
npm install -g ntfy-reverse-proxy
```

Or run it directly without installing:

```bash
npx ntfy-reverse-proxy
```

Both `ntfy-reverse-proxy` and `nrp` are registered as CLI aliases — they do the same thing.

The first command that needs configuration copies the starter template included with the npm package to your platform config directory. Global and `npx` installs don't require a repository clone or a separately downloaded `config.sample.json`.

## First-Time Setup

The interactive config menu starts from the packaged template and guides you through everything you need for a working deployment.

1. Run `nrp` to launch the interactive config menu.
2. **Add at least one ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology>.** Each <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> needs a name, a URL starting with `https://`, and a token starting with `tk_`.
3. **Add at least one <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>.** Choose a name, <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology>, <Terminology title="The ntfy channel your phone subscribes to for alerts" to="/docs/reference/terminology#ntfy-servers-and-messages">topic</Terminology>, delivery mode, and assign one or more <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">servers</Terminology>.
4. **Update settings.** Set the `worker_name` and `base_domain` to match your Cloudflare domain.
5. **Run `nrp validate`** from the CLI to check config integrity. Validation also runs automatically as part of the deploy step. This catches missing fields and invalid references before deployment.
6. **Run deploy** to generate `wrangler.toml` and deploy to Cloudflare Workers.

The generated Worker configuration includes a SQLite-backed Durable Object automatically. You do not need to create a queue or database. It provides [durable delivery](/docs/features/durable-delivery/) by keeping a separate FIFO notification lane for each context.

:::tip
The CLI validates config against its schema on every load. You can also run the full validation manually with `nrp validate`, and **Deploy** in the interactive menu runs it before deploying.
:::

## Sending Your First Notification

After deployment, each HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> gets a subdomain route in the format `{context-id}.{base_domain}`. Test it with a simple `curl` command.

### Plain Text Notification

```bash
curl -X POST https://{context-id}.ntfy.example.com \
  -H "Content-Type: text/plain" \
  -d "Hello from ntfy-reverse-proxy!"
```

### Authenticated Notification

If the <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> has a token configured, include the `Authorization` header:

```bash
curl -X POST https://{context-id}.ntfy.example.com \
  -H "Authorization: Bearer your-context-token" \
  -d "Authenticated notification"
```

### Landing Page

GET requests to any <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> URL return a <Terminology title="Open a context's URL in a browser to see it's up" to="/docs/reference/terminology#configuration">landing page</Terminology> showing "Reverse Proxy for ntfy" with an operational status badge. When `show_response_output` is enabled, the page also includes a collapsible section with the full configuration, with sensitive values masked.

## If Something Goes Wrong

If deployment fails or notifications are not arriving, check [Troubleshooting](/docs/reference/troubleshooting/). Common first-time issues include:

- Cloudflare's bot protection blocking webhooks (403 errors)
- DNS propagation delays after deployment
- ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> misconfiguration
