Deploy Reverse Proxy for ntfy to Cloudflare Workers and configure DNS, SSL, and <Terminology title="Each context gets its own subdomain on Cloudflare" to="/docs/reference/terminology#cloudflare-setup">custom domain routes</Terminology>.

## Cloudflare Requirements

- **Cloudflare account** — Free or paid. The deployment uses Workers and SQLite-backed Durable Objects; current plan limits and pricing apply.
- **Registered domain** — You need a domain managed by Cloudflare DNS. Cloudflare Registrar offers domains at cost with no markup.
- **Cloudflare API token** — Deploy uses a Cloudflare API token with the permissions listed below, both for its own Cloudflare calls and to run Wrangler (Cloudflare's deployment CLI). It reads `CLOUDFLARE_API_TOKEN` from your environment or `.env` file, and **Deploy** in the interactive menu walks you through creating one.

## How Deployment Works

The deploy command runs these steps in sequence:

```mermaid
flowchart TD
    Start[Deploy Command] --> ResolveToken[Resolve API Token]
    ResolveToken --> Validate[Validate Config]
    Validate --> Verify[Verify Permissions]
    Verify --> KV[Ensure KV Namespace]
    KV --> Generate[Generate wrangler.toml]
    Generate --> DeployWorker[Deploy Worker]
    DeployWorker --> EmailCheck{Email Contexts?}
    EmailCheck --> SetupEmail[Setup Email Routing]
    EmailCheck -.-> Readiness
    SetupEmail --> Readiness[Check Readiness]
    Readiness --> Summary[Print Summary]
```

1. **Resolve API token** — Reads `CLOUDFLARE_API_TOKEN` from the environment or `.env`. If it's missing or invalid, **Deploy** in the interactive menu prompts for a new one and saves it, while `nrp deploy` stops with an error.
2. **Validate** — Checks config integrity (schema, <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> references, duplicate IDs).
3. **Verify permissions** — Confirms the API token has access to Workers Scripts, Workers Routes, Workers KV Storage, and (if email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> exist) Email Routing Rules.
4. **Ensure <Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology>** — Creates or locates a Cloudflare Workers <Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology> for Statuspage deduplication and session tokens. The namespace ID is automatically passed to the <Terminology title="Generated from config.json for Wrangler to deploy" to="/docs/reference/terminology#cloudflare-setup">wrangler.toml</Terminology> generator.
5. **Generate** — Produces `wrangler.toml` next to your `config.json` with all routes and bindings, plus a copy of your config in `.wrangler/ntfy-reverse-proxy/` beside it that ships inside the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology>.
6. **Deploy <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology>** — Invokes `wrangler deploy` to push the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> to Cloudflare.
7. **Setup email routing** — If email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology> exist, automatically configures <Terminology title="Lets an email address trigger the proxy like a webhook" to="/docs/reference/terminology#cloudflare-setup">Cloudflare Email Routing</Terminology> rules to forward emails to the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology>.
8. **Check readiness** — Confirms each HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology>'s custom domain is attached to the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> and resolves on public DNS through Cloudflare's resolver (1.1.1.1), waiting up to a minute and naming any host that is still pending. With email contexts, it also checks that the base domain's MX records point at Cloudflare Email Routing. These checks only warn; deploy again later to recheck a pending host.
9. **Print summary** — Displays deployed <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> URLs and email addresses.

## Generated wrangler.toml

The generated file includes:

- **Routes** — Each HTTP <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> gets a <Terminology title="Each context gets its own subdomain on Cloudflare" to="/docs/reference/terminology#cloudflare-setup">custom domain route</Terminology>: `{context-id}.{base_domain}`. Cloudflare automatically creates DNS records for <Terminology title="Each context gets its own subdomain on Cloudflare" to="/docs/reference/terminology#cloudflare-setup">custom domain routes</Terminology>.
- **Email routing** — Comments showing which email addresses need to be configured in <Terminology title="Lets an email address trigger the proxy like a webhook" to="/docs/reference/terminology#cloudflare-setup">Cloudflare Email Routing</Terminology> for email <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology>.
- **Bundled config** — `main` points to a generated entry in `.wrangler/ntfy-reverse-proxy/` that ships your config inside the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> instead of as environment variables, which Cloudflare caps at 5 KB each (about 20 <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">contexts</Terminology>). The <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> checks the config once when it starts instead of on every request and email.
- **Durable Object** — Binds the SQLite-backed `DELIVERY_OUTBOX` class and declares its initial migration. This provides one logical FIFO lane per context without Cloudflare Queues, D1, or R2.
- **<Terminology title="Remembers Statuspage incidents so you aren't told twice" to="/docs/reference/terminology#cloudflare-setup">KV namespace</Terminology>** — Deploy binds the namespace it found or created in step 4 (used by the Statuspage <Terminology title="Turns one app's raw alert into a clean ntfy message" to="/docs/reference/terminology#how-it-works">interpreter</Terminology> for deduplication and by <Terminology title="A short-lived, one-use pass a sender gets from /session" to="/docs/reference/terminology#configuration">session tokens</Terminology>). `nrp generate` leaves this binding out.

The Durable Object does not need a separate provisioning step. It is created through the generated binding and migration when Wrangler deploys the Worker. See [Durable Delivery](/docs/features/durable-delivery/) for retry behavior and cost considerations.

:::warning
`wrangler.toml` and the `.wrangler/` folder are gitignored because they contain your <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> IDs and a copy of your config with its tokens. Do not commit them to version control.
:::

## DNS and SSL

After deployment:

- Cloudflare automatically creates DNS records for <Terminology title="Each context gets its own subdomain on Cloudflare" to="/docs/reference/terminology#cloudflare-setup">custom domain routes</Terminology>. Propagation typically takes a few minutes.
- SSL certificates are provisioned automatically by Cloudflare. This can take up to 15 minutes.
- Your SSL/TLS mode should be set to "Full" or "Full (strict)" in the Cloudflare dashboard.

## Custom Domain Routes

Routes use `custom_domain = true`, meaning the subdomain is the first part of the hostname. Traditional Cloudflare routes (with `custom_domain = false`) are not supported because the <Terminology title="The proxy itself, running on your Cloudflare account" to="/docs/reference/terminology#how-it-works">worker</Terminology> matches the hostname's subdomain against <Terminology title="One alert source: its address, interpreter, and topic" to="/docs/reference/terminology#how-it-works">context</Terminology> IDs.

## Configuring Your ntfy Servers

For the proxy to work correctly, each ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology> should have:

- `base-url` set to the <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology>'s public URL
- `behind-proxy` set to `true`
- `attachment-cache-dir` configured if you use an <Terminology title="Where you hear about alerts the proxy couldn't handle" to="/docs/reference/terminology#ntfy-servers-and-messages">error topic</Terminology>, because the proxy sends error details as an `error-debug.json` <Terminology title="A file sent along with the notification" to="/docs/reference/terminology#ntfy-servers-and-messages">attachment</Terminology>. Without this, ntfy cannot store uploaded files.

The proxy automatically splits messages exceeding 4000 UTF-8 bytes into <Terminology title="Long messages arrive as (1/3), (2/3), (3/3)" to="/docs/reference/terminology#ntfy-servers-and-messages">numbered parts</Terminology>. This is handled by the proxy, not the ntfy <Terminology title="One of your ntfy instances: a name, URL, and token" to="/docs/reference/terminology#ntfy-servers-and-messages">server</Terminology>.

:::tip
ntfy's default attachment limits are: 15 MB per file (`attachment-file-size-limit`), 5 GB total storage (`attachment-total-size-limit`), and 3-hour expiry (`attachment-expiry-duration`). Adjust these based on your storage capacity and retention needs. Refer to the [ntfy self-hosting documentation](https://docs.ntfy.sh/config/) for full configuration options.
:::
